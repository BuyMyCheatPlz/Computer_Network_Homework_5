# LCP 1 局域网通信协议设计规范 (LAN Chat Protocol v1)

本规范定义了局域网聊天室系统的应用层通信协议（LCP 1，LAN Chat Protocol Version 1）。该协议运行在传输层 TCP 与 UDP 之上，由 Python 客户端与 C++17 服务端共同实现，支持局域网内的可靠控制、多人群聊组播与定向私聊。

---

## 一、 协议设计背景与总体设计思想

### 1. 为什么需要自研应用层协议？
在 TCP/IP 体系结构中，传输层的 TCP 和 UDP 仅负责把数据字节或数据报从一台主机的端口传递到另一台主机的端口，并不理解业务数据的含义。应用层协议的作用在于定义：
* **数据如何界定边界**（保证应用报文能够被无歧义地完整拆分）；
* **通信双方的消息类型与参数格式**（如登录、发消息、拉取名单）；
* **数据的安全与完整性校验规则**（防止网络误码与报文篡改）；
* **异常情况下的应答与容错机制**。

### 2. 双通道传输设计（TCP 控制 + UDP 组播）
为了在局域网多人并发交流中取得**“高可靠性”**与**“高传输效率”**的最佳平衡，本协议设计了双通道传输模型：
* **TCP 可靠控制通道（默认端口 45860）：**
  面向连接，提供全双工、顺序可靠的字节流交付。用于承载用户注册、登录认证、在线成员动态推送、心跳保活、定向私聊以及超时单播补发。
* **UDP 高效组播通道（组播地址 239.255.42.99:45861）：**
  无连接，利用 Class D 类 IP 组播技术。当服务端转发群聊消息时，只需向该地址投递一次数据包，由局域网底层交换机/路由器向所有加入组的客户端高效复制分发，大幅优化了多人群发时的局域网带宽利用率。设置 `TTL=1` 将组播流量严格限制在当前物理子网内。

## 二、 数据帧结构与定界机制

### 1. TCP 字节流定界（解决粘包与拆包）
TCP 是基于流（Stream）传输的，连续发送的多条消息在接收端可能粘连（粘包），单条较大消息也可能被分段传输（拆包）。为此，LCP 1 在 TCP 传输中引入了**长度前缀定界法**：

```text
+-----------------------+------------------------------------------+
|  4 字节包体长度 (N)    |           N 字节 JSON 报文正文            |
| (大端无符号整数 uint32) |              (UTF-8 编码)                |
+-----------------------+------------------------------------------+
```

* **长度前缀：** 占用 4 字节，采用网络标准大端字节序（Big-Endian），其数值 $N$ 表示后续 JSON 报文正文的精确字节数（有效范围：$1 \le N \le 32768$ 字节）。
* **接收端定界流程：**
  1. 接收线程启动阻塞循环，直到精准读取满 4 字节，解析出长度 $N$；
  2. 若 $N$ 超出安全范围，判定为非法帧并主动断开异常连接；
  3. 再次启动循环读取，直到在底层接收缓冲区中精准收集满 $N$ 字节；
  4. 将这 $N$ 字节完整提交给 JSON 解析器。由此彻底解耦粘包与拆包问题。

### 2. UDP 组播数据报
UDP 本身是基于数据报（Datagram）传输的，操作系统内核在传输层已经严格保留了报文边界，因此 UDP 组播数据报**不包含** 4 字节长度前缀，直接携带完整的 JSON 文本。

## 三、 统一报文格式规范

LCP 1 的所有交互数据均以标准 JSON 格式进行封装，顶层必须且仅允许包含以下 6 个核心字段：

```json
{
  "v": 1,
  "id": "e4d909c290d0fb1ca068ffaddf22cbd0",
  "type": "CHAT",
  "ts": 1793400000000,
  "body": {
    "mode": "all",
    "targets": [],
    "text": "同学们好，这是通过 UDP 组播发送的群聊消息！"
  },
  "checksum": "8f4a7c... (64位十六进制散列值)"
}
```

| 字段名 | 数据类型 | 规格约束 | 设计含义与作用 |
| :--- | :--- | :--- | :--- |
| `v` | 整数 | 固定为 `1` | 协议版本号（Protocol Version），便于未来平滑升级扩展。 |
| `id` | 字符串 | 32 位小写十六进制 | 每条消息唯一的随机标识符（UUID），用于请求匹配、去重及 ACK 确认。 |
| `type` | 字符串 | 1~40 字符，大写 | 业务任务类型码（如 `LOGIN`、`CHAT`、`RESULT` 等）。 |
| `ts` | 整数 | 13 位 Unix 毫秒时间戳 | 报文发送时的客户端/服务端本地时间，供展示与计时参考。 |
| `body` | JSON 对象 | 键值对对象 | 具体业务的参数载荷（Payload）。 |
| `checksum`| 字符串 | 64 位小写十六进制 | 报文完整性散列值，由 SHA-256 算法生成。 |

## 四、 报文完整性校验原理与算法

### 1. 为什么选择 SHA-256 完整性校验？
网络传输可能由于信道电磁干扰出现比特翻转，或者受到局域网内恶意第三方的篡改。SHA-256 是一种具备高抗碰撞性与显著“雪崩效应”的单向安全散列算法：输入数据的任何 1 个比特发生变动，输出的 256 位（64 位十六进制）散列值就会发生天翻地覆的随机化改变。

### 2. 校验与计算步骤
1. **标准化序列化：**
   发送端提取除 `checksum` 以外的 5 个顶层字段（`v`, `id`, `type`, `ts`, `body`）。为了防止不同编程语言在序列化 JSON 时因字段键序不同导致哈希值不一致，协议强制要求：
   * 所有对象的键名必须按**字典序（Alphabetical Order）**递归排序；
   * 采用无额外空格和换行的紧凑格式（分隔符为 `,` 与 `:`）；
   * 中文字符保持原生 UTF-8 编码，不转义为 Unicode 转义字符。
2. **计算散列摘要：**
   将上述标准化序列化得到的 UTF-8 字节流 $M$ 传入 SHA-256 散列函数，得到 32 字节摘要，并转换为 64 位小写十六进制字符串，填入 `checksum`。
3. **接收端验算与拦截：**
   接收端收到报文后，以完全一致的规则对剩余字段重算 SHA-256 摘要，并与接收到的 `checksum` 进行逐字节比对。若两散列值不吻合，判定报文遭到篡改或发生传输误码，服务端返回 `BAD_CHECKSUM` 错误码并丢弃该请求，绝不执行业务逻辑。

## 五、 客户端核心业务交互流程

### 1. 账号注册与安全存储 (`REGISTER`)
* **请求载荷：** `body: { "name": "张三", "password": "密保密码" }`
* **处理逻辑：**
  * 服务端验证用户名格式（1~20 字符，支持中文、英文字母、数字及下划线）与密码长度（6~128 字符）。
  * 检查用户是否已存在。若不存在，服务端生成 16 字节的高强度随机“盐值”，并使用 **PBKDF2-HMAC-SHA256（200,000 次迭代）** 计算出派生密钥散列。
  * 将 `(用户名, 盐值, 派生散列)` 原子更新持久化到磁盘文件 `accounts.json`。
* **响应：** 返回 `RESULT`，包含 `ok: true/false` 与状态说明。

### 2. 用户登录与状态建立 (`LOGIN`)
* **请求载荷：** `body: { "name": "张三", "password": "密保密码" }`
* **处理逻辑：**
  * 服务端根据用户名读取存储的盐值与哈希，重新执行 PBKDF2 运算，比对密码是否正确。
  * 检查该账号是否已在其他连接登录（维护单一在线会话）。
  * 登录成功后，将该 TCP 连接标记为“已认证”并绑定该用户名，随后向当前所有在线客户端广播最新的成员列表。
* **响应：** 包含服务端的房间实例 ID、组播 IP 地址与 UDP 端口。客户端据此调用系统底层 API 加入组播组（`IP_ADD_MEMBERSHIP`）。

### 3. 多人群聊发送与接收 (`CHAT, mode: "all"`)
* **发送流程：**
  1. 客户端通过 TCP 发送聊天请求：`body: { "text": "大家好", "mode": "all", "targets": [] }`；
  2. 服务端鉴权后，获取当前所有在线用户列表，在内存中为每位成员建立“待确认条目”，设定 800ms 超时截止时间；
  3. 服务端通过 UDP Socket 向组播组 `239.255.42.99:45861` 发送一次组播数据报。
* **确认与可靠补发（ACK + TCP Fallback）：**
  1. 客户端在本地组播套接字收到该消息，验证无误后，通过 TCP 向上层服务回发确认消息：`type: "ACK", body: { "message_id": "xxx" }`；
  2. 服务端收到 ACK 后，从待确认表中清除该用户的记录；
  3. **超时补发机制：** 服务端后台线程每 100ms 扫描一次待确认表。若某在线用户在 800ms 内因网络丢包未送达 ACK，服务端立即通过该用户的 TCP 稳定连接将原消息重发一次；
  4. **去重保障：** 客户端维护滑动窗口缓存（记录最近 2048 个已接收消息 ID），若先后收到组播与 TCP 补发，自动过滤重复消息，确保聊天界面仅渲染一次。

### 4. 选定多人定向私聊 (`CHAT, mode: "selected"`)
* **请求载荷：** `body: { "text": "悄悄话", "mode": "selected", "targets": ["李四", "王五"] }`
* **物理隔离机制：**
  * 服务端校验所有目标用户必须当前在线；
  * 服务端**不向组播组发送任何数据**，而是遍历目标用户的 TCP 连接，逐个单播推送 `MESSAGE` 报文，并回显一份给发送者本人；
  * 未被选中的其他用户在物理网络链路上根本不会收到该数据包，从网络层和传输层实现真正的定向隔离，保障了定向通信内容的私密性。

### 5. 心跳保活与异常断开检测 (`PING / PONG`)
* 客户端每隔 4 秒通过 TCP 向服务端发送一次 `PING` 探活报文，服务端回复 `PONG`。
* 服务端为每个连接维护读超时（15 秒）。若客户端异常断开，服务端能在超时到达或底层检测到连接重置（RST/FIN）时，迅速释放套接字资源，将离线用户从在线列表中剔除，并自动向剩余在线成员推送更新后的在线名单。

## 六、 错误码与应用层容错设计

协议定义了一套完备的错误状态码。当客户端发送异常数据或非法参数时，服务端会优雅地返回包含具体错误码的 `ERROR` 报文，保障主服务进程持续稳定运行：

| 错误代码 (Error Code) | 触发条件 | 系统应对策略与连接状态 |
| :--- | :--- | :--- |
| `BAD_PACKET` | 数据帧不是合法 JSON、编码非 UTF-8 或嵌套过深 | 丢弃当前错误报文，保留 TCP 连接，继续接收后续报文 |
| `BAD_CHECKSUM` | 报文 SHA-256 摘要比对失败，数据遭篡改或损坏 | 拒绝执行业务，返回错误提示 |
| `INVALID_TASK` | 报文格式正确，但 `type` 为未知或未定义任务码 | 返回任务不存在错误，连接正常维持 |
| `FRAME_TOO_LARGE` | 数据帧长度超过 32KB 规格上限 | 判定为非法异常流量，主动断开异常连接 |
| `AUTH_FAILED` | 用户名不存在或密码校验错误 | 拒绝登录，保持当前连接为未认证状态 |
| `ALREADY_ONLINE` | 该账号当前已在其他连接登录 | 保持单一在线会话，返回冲突提示 |
| `NOT_LOGGED_IN` | 客户端在未登录状态下尝试发送聊天或拉取名单 | 拦截请求并提示需先完成身份认证 |
| `NO_RECIPIENT` | 定向私聊的目标列表为空，或其中包含已离线的成员 | 整条消息不予发送并提示发送方检查好友在线状态 |
| `REPLAY` | 本连接短时间内重复提交相同 ID 的业务请求 | 拦截重复操作，防止表单重复提交 |

---

## 七、 总结

LCP 1 协议充分体现了计算机网络协议设计的核心原则：
1. **分层解耦：** 底层利用 TCP 保证连接与认证的高可靠，利用 UDP 组播保证多人群发的高效率；
2. **严格定界：** 长度前缀法彻底解决 TCP 流式传输粘包拆包；
3. **数据完整：** SHA-256 标准化散列实现精准防误码与防篡改；
4. **稳健容错：** 应用层 ACK 补发机制为无连接组播通信提供了坚实可靠的消息必达保证，完善的错误码体系保障了系统的高可用性与健壮性。
