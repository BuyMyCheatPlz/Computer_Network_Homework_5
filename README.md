# 局域网多人聊天室系统 (LAN Chatroom)

本系统是面向《计算机网络》课程设计开发的局域网多人聊天应用，采用标准的 **C/S（客户机/服务器）架构**。客户端采用 **Python 3.10+ (Tkinter)** 开发，提供直观友好的图形界面；服务端采用高性能的 **C++17 (Winsock2)** 实现底层网络并发调度与状态管理。

项目充分融合了传输层 **TCP（传输控制协议）** 与 **UDP（用户数据报协议）** 的各自优势，群聊采用高效的 **IPv4 组播（Multicast）** 技术，定向私聊与状态控制采用可靠的 **TCP 单播**，并在应用层自研了数据帧定界、ACK 确认补发、SHA-256 完整性防篡改及 PBKDF2 密码加盐存储等核心机制。

## 核心网络原理与设计思想

为了帮助理解底层计算机网络运行机制，本项目在设计中深入落实了以下核心原理：

### 1. 为什么采用“TCP + UDP 组播”混合架构？
* **群聊下行带宽开销优化（为什么优选 UDP 组播）：** 在多人聊天场景下，若使用传统的 TCP 点对点单播，当一个群内有 50 人在线时，服务端每转发一条群聊消息，都需要在 50 条独立的 TCP 连接上分别复制发送 50 次，造成服务器 CPU 与网络出口带宽随人数线性增加。组播（Multicast）利用 Class D 类 IP 地址（本项目使用 `239.255.42.99:45861`）。服务端仅需向该组播地址**发送一次数据包**，底层的局域网交换机和网卡硬件即可自动识别并将数据包高效分发给所有加入了该组播组的主机，极大地节约了网络带宽资源。
* **控制信令与定向私聊采用 TCP：** TCP 提供面向连接的三次握手、顺序确认与链路保活机制，非常适合用户注册、登录身份认证及在线成员列表的实时同步；在定向私聊时，TCP 单播仅将数据推送至指定目标的 Socket 连接，未被选中的第三方用户在物理链路上完全不会收到该数据包，天然实现物理级数据隔离。
* **TTL=1 本地广播域控制：** 组播报文的 IP 首部 TTL（Time to Live，生存时间）被严格设置为 1。这意味着组播数据包每经过一台路由器，TTL 就会减为 0 并被丢弃，从而保证组播通信严格限制在当前本地局域网（同一子网）内部，既防止数据外溢，也避免对外部网络造成广播风暴。

### 2. UDP 组播“不丢消息”的应用层可靠性保证
* **传输设计原理：** UDP 作为无连接协议具备高吞吐、低延迟优势。为保障群聊消息在偶发网络抖动环境下的交付质量，系统在应用层自主设计了高可靠闭环：
  1. **组播发送与定时：** 服务端向组播组发送一条群聊消息后，在内存中为每位在线成员记录待确认条目，并启动 800ms 超时计时器。
  2. **客户端回传 ACK：** 客户端收到组播消息并验证无误后，立即通过可靠的 TCP 链路向服务端回送一条确认报文（ACK）。
  3. **超时单播补发：** 若 800ms 后服务端仍未收到某位在线成员的 ACK，判定该成员需要可靠补偿，服务端将立即通过该用户稳定的 TCP 单播通道重新补发原消息。
  4. **窗口去重：** 客户端维护最近接收的消息唯一标识（ID）缓存，若短时间内同时收到组播副本与 TCP 补发副本，仅展示首份到达的消息，自动过滤重复数据，实现“既享组播高效，又保消息必达”。

### 3. 如何解决 TCP 字节流的“粘包与拆包”？
* **传输设计原理：** TCP 是面向字节流（Byte Stream）的传输协议，在传输层不维护应用层消息的结构边界（连续小包可能合并，大包可能分段）。为使接收端能精确识别每个业务报文，系统自研了数据帧定界机制：
  * **定界方案：** 本协议采用经典的 **“4 字节定长头部 + JSON 数据体”** 定界机制。
  * 头部为 4 字节无符号整数（采用网络标准大端序 `uint32_be`），明确标注后续消息体的实际字节长度 $N$。
  * 接收端处理逻辑：先通过循环阻塞读取直至收满 4 字节，解析出长度 $N$；接着再次循环读取直至精确收满 $N$ 字节，才将其交付上层 JSON 反序列化。从根本上杜绝了粘包和拆包引发的数据解析混乱。

### 4. 报文完整性校验与防篡改（SHA-256）
* **传输设计原理：** 为验证局域网传输过程中数据内容的绝对完整性与真实性，系统引入了单向安全散列算法：
  * **算法实现：** 发送方在构造报文时，将协议版本、随机消息 ID、任务类型、时间戳及消息内容进行标准化字典序排列，使用 SHA-256 安全散列算法计算出 64 位十六进制散列值，作为 `checksum` 填入报文尾部。
  * **接收端验证：** 接收方收到报文后，排除 `checksum` 字段，以完全相同的算法重新计算散列值并比对。由于 SHA-256 的雪崩效应，数据哪怕发生单比特改变，散列值也会发生彻底变动，接收端能精准识别受损或被篡改的报文并直接安全丢弃，不执行业务逻辑。

### 5. 账号密码安全存储机制（PBKDF2 随机加盐）
* **存储设计原理：** 遵循信息安全规范，用户凭证存储采用不可逆的单向加盐散列机制，防范离线字典碰撞：
  * **实现方案：** 系统在注册时，为每个用户生成 16 字节的高强度真随机“盐值（Salt）”，并结合用户密码，通过基于 HMAC-SHA256 的密钥派生函数 **PBKDF2** 开展 **200,000 次** 高强度循环迭代运算，生成 32 字节的派生哈希值存储于本地。
  * **安全效果：** 随机盐消除了多用户同密码的哈希相同性，使得彩虹表彻底失效；20 万次迭代运算大幅提高了暴力尝试的时间成本。

## 快速开始

本项目开箱即用。已提供预先静态编译好的服务端二进制文件 `bin/chat_server.exe`，单机测试只需安装 Python 即可运行。

1. **环境准备：** 确保电脑已安装支持 Tkinter 的 Python 3.10 及以上版本（可通过 `python -m tkinter` 检验环境）。
2. **一键启动：** 双击根目录下的 `start.bat`，即可唤起图形客户端；或在终端中运行：
   ```powershell
   python -m lan_chat
   ```
3. **启动内置服务端：** 在主界面的“服务器管理”标签页中，点击 **“启动服务器”** 按钮（单机体验保持默认监听地址 `0.0.0.0` 及端口 `45860` 即可）。
4. **账号注册与登录：** 切换到“聊天室”标签页，输入用户名与密码（至少 6 位），先点击 **“注册”**，注册成功后再点击 **“登录”**。
5. **多用户协同与私聊隔离验证：**
   * 保持服务端运行，在同一台电脑上再双击运行一次 `start.bat`（或新开终端运行 `python -m lan_chat`），打开第 2 个、第 3 个客户端窗口并分别注册登录新账号。
   * **群发消息：** 输入文字点击“群发”，所有在线客户端均可同步收到消息，日志显示为 `UDP 组播`。
   * **定向私聊：** 在右侧在线成员列表中按住 Ctrl 或单击多选指定好友，点击“发送给选中成员”，此时仅有被勾选的好友能收到该私聊消息，未被勾选的旁观者在网络链路上完全接收不到，实现物理级别的定向隔离。
6. **注销与退出：** 点击“注销”可安全退出登录状态（账号信息保存在服务端磁盘中）；关闭窗口时会自动向服务端发送断开信令并释放系统资源。

## 局域网多电脑联机指南

当在实验室、宿舍或教室使用两台或多台实体电脑联机时，请按以下步骤操作：

1. **接入同一网络：** 确保所有电脑接入同一个 Wi-Fi 或有线局域网路由器（处于同一 IP 网段，例如 `192.168.1.xxx`）。
2. **查询服务器 IP：** 在充当服务端的电脑上打开终端，运行 `ipconfig`，找到当前正在使用的局域网 IPv4 地址（如 `192.168.1.100`）。
3. **启动服务端：** 服务端监听地址保持 `0.0.0.0`；若服务端电脑有多个网卡或开启了虚拟网卡/VPN，请在“组播出口 IPv4”处明确指定该局域网网卡的 IP。
4. **客户端连接：** 在其他电脑上打开客户端，将“服务器 IPv4”修改为服务端的真实 IP 地址（如 `192.168.1.100`），点击连接并登录。
5. **网络适配与自愈特性：**
   * 初次运行时，Windows 防火墙若弹出网络访问提示，请点击“允许访问”。
   * 若特定网络环境（如开启了 AP 客户端隔离策略的 Wi-Fi）限制了组播报文转发，系统设计的**可靠性自愈机制**会自动生效：群聊消息在未收到组播 ACK 时，会在约 0.8 秒后通过 TCP 单播自动补发到达，确保通信通畅。聊天记录中标明 `UDP 组播` 代表成功通过局域网组播接收，标明 `TCP` 则代表经由可靠通道补发到达。

## 自动化测试验证

系统附带了 12 项覆盖全面的自动化集成测试，可真实启动 C++ 服务端进程并建立并发网络连接进行检验：

```powershell
python -m unittest -v tests.test_chat
```

测试覆盖了包括中英文字符集编解码、报文篡改拦截、格式容错、密码加盐校验、真实 UDP 中文组播、定向私聊隔离、网络丢包超时补发、异常任务码恢复、TCP 粘包拆包定界恢复以及服务端重启持久化等全部关键场景，确保系统在复杂网络环境下的鲁棒性。
